# 日常使用：Chat → Issue → Codex → 草稿 PR → Chat

仓库：[chat-codex-handoff-demo-20261009](https://github.com/yujiacheng671/chat-codex-handoff-demo-20261009)。这是公开的纯文档演示项目，只放演示材料；真实项目需单独确认仓库和授权。

## 每次怎么用

1. 在普通 Chat 中讨论清楚目标、允许修改的文件和验收条件，然后说：**“交接 Codex：把刚才确认的方案建成演示仓库的 Issue，只记录最终决定和验收条件。”** Chat 先查重，创建后返回真实链接。
2. 将该 Issue 链接发给桌面 Codex：**“执行这个 Issue：〈链接〉。读取 AGENTS.md，在独立分支完成必要检查，创建草稿 PR 并将链接回填 Issue；不合并、不部署。”** 这是当前已采用的执行入口，需要一次链接交接。
3. 回到同一个普通 Chat 说：**“验收刚才的 Issue：读取其关联 PR、实际 diff 和当前提交的检查证据，逐条给出通过、需修改或证据不足。”** Chat 从 Issue 找到 PR，无需重新复制完整讨论或代码。
4. 如需修正，一次汇总确认的问题，要求 Codex 沿用原分支与 PR。最终是否合并由用户决定。

- 在 Issue 中发送原生 Codex 触发评论后，[官方机器人回复需要为仓库创建环境](https://github.com/yujiacheng671/chat-codex-handoff-demo-20261009/issues/3#issuecomment-6086361357)，没有提供执行任务。其设置链接在当前账号跳回首页；不能把机器人回复认定为已开始实施。

- 本次 PR 通过连接器创建，不依赖用户在云端界面点击“创建 PR”。其他云端入口是否需要该点击应按实际界面记录，尚未验证。
- 返回 Chat 的验收通过明确请求启动；尚未安装无人值守的 PR 完成通知或自动验收。跨会话读取有时返回正文引用占位符，用户可直接在原 Chat 查看审阅。

## 验收证据放在哪里

本任务基线为 `84736a95fd6781263a5181d8817adec9f60e4a57`。最终 head、精确文件范围、实际检查命令和退出结果写在关联 PR 正文与 Issue 回填评论中；检查必须对应最终提交。

文档任务检查 `git diff --check <base> <head>`，并确认差异恰好为 `docs/daily-use.md`。仓库未配置 CI，不能写成“CI 通过”。Chat 可以复核记录和差异，但应区分作者提交的本地检查证据与自己独立执行的检查。

## 节省额度与执行边界

先在普通 Chat 确认范围，再启动一次 Codex；只传最终决定和相关文件路径，返工集中处理。按任务运行必要检查，不默认开启轮询、多代理或每个 PR 的自动审阅。实际额度消耗依模型、上下文和任务而变，不承诺固定节省比例。

禁止自动合并、部署、真实交易、访问密钥、修改工作流或新增依赖服务。
